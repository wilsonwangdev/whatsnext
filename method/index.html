方法 / Method

先定义事实，再讲故事。

一份关于收购的档案，最容易犯的错误是把公告当结果、把传闻当事实、把融资额当交易价。 这一页说明我们如何分类、如何标注证据、如何处理不确定，以及如何纠错。

01 / 收录范围

本档案收录开发者软件、开源项目与相关团队的收购、控股权交易、人才收购、团队加入， 以及被公开终止的交易。判断标准不是交易金额，而是它对开发者生态有可观察的影响。

时间范围：2018 年至今。起点定在 2018 年，是因为微软收购 GitHub 确立了此后同类交易的判断框架——“保持独立”“继续免费”这套承诺话术从这里开始成为标准动作。 早于此的案例虽有价值，但缺少可直接对照的后续记录，容易变成转述而非核验。

我们优先收录满足以下任一条的案例：

  • 产品被大量开发者日常使用，或作为依赖出现在供应链中。可核查门槛（满足其一即可）：GitHub 仓库 5,000 星以上、npm 周下载量 100 万以上、 或被 Debian / Homebrew / nixpkgs 等主流发行渠道收录；
  • 交易涉及开源许可证、治理结构或社区承诺的变化；
  • 收购后的产品走向（继续、整合、停运）有明确的一手记录可追踪；
  • 交易结构本身有代表性，能说明一类路径（例如上市后补强、平台整合、监管否决）。

时间沉淀要求：交割不满 24 个月的交易，只进入观察名单，不列为案例。 公告写的是意图，24 个月之后才有足够的一手记录判断它兑现了多少。 唯一的例外是已公开终止的交易——终止本身就是结果，不需要等待。

不收录：纯财务投资、无公开记录的传闻交易、以及无法核验的“据说”。

02 / 交易分层

把“被收购”当成一个统一说法，是这类记录最常见的失真来源。我们按公开可确认的程度分层：

整体收购收购方取得标的公司 100% 股权。通常有双方公告或监管文件。
控股权取得多数股权但保留少数股东；控制权转移，法律主体可能不变。
人才收购以获取团队为主要目的，可能伴随技术授权或资产转让，但不一定收购公司主体。
团队加入团队整体加入收购方，交易结构、对价与主体安排未披露。不能等同于公司被收购。
资产收购只买代码、商标或特定业务，不承接公司主体与负债。

写作规则：如果公告只说“团队加入”，档案就写“团队加入”，并在状态栏标注； 不会因为收购方把它归入 Acquisitions 分类，就改写成“已收购”。

03 / 证据等级

每条案例都标注一个证据等级，表示核心事实（交易、对价、时间）的可核验程度。

A交易双方均有一手公告，或存在监管文件（如 20-F、8-K、招股书）直接支持。 可直接引用。
B一方有一手公告，或权威媒体基于工商登记、监管记录报道。引用时应说明另一方缺失。
C仅见二手报道，未找到一手来源。档案会保留该案例，但明确标注“待核验”， 并限制结论强度。

证据等级不是永久标签。找到新来源时可以升级，也可以在发现错误时降级——每次变更记录在提交历史里。

04 / 时间精度

时间线只记录来源能支持的精度。如果只知道年份，就显示年份；只知道月份，就显示月份。 日期用于排序时统一记为当月或当年第一天，但显示时使用来源可支持的粒度。

交易状态与日期分开记录：

  • 公告日期：双方首次公开宣布的日期；
  • 完成日期：交割、工商变更或监管批准完成的日期；
  • 两者可能相隔数月甚至一年以上，不能混用。

时间线只记录已经发生的事件。已公布但尚未发生的日期放在「已公布的计划」， 并标注它是公告给出的日期，还是按公告期限推算；某个时点的静态状态（例如许可证现状） 放在「状态核查」，不混入时间线。

05 / 承诺核对

收购公告里的承诺，是这份档案最有价值的部分，也是最容易被遗忘的部分。 我们把公告中的可检验表述摘出来，逐条跟踪：

已兑现有明确证据表明承诺被完整执行。
部分兑现方向一致，但范围、力度或时间表打了折扣。
待观察承诺期未到，或暂时没有足够信息判断。
未兑现承诺期已过，且有证据表明未执行。
无法判断承诺本身模糊，或缺少可观察的指标。

“无法判断”是正常结论。把模糊承诺强行判成“已兑现”或“未兑现”，都会损害档案的可信度。

团队类承诺怎么判

“保留团队”“维持独立运营”“不减员”是收购公告里出现频率最高的承诺，也是最难核对的一类。 问题在于团队人数在多数交易里根本拿不到：非上市公司不披露员工数，小团队从不公开， 被大公司收购后标的通常被并入某个部门，从此在财报里消失。

因此我们按以下顺序取证据，并在页面上标明用的是哪一种：

  1. 人数——有官方口径（公告、年报、监管文件）时优先使用。 第三方劳动力数据仅在口径可确认时采用；多个来源差异超过一倍时，不采信任何单一数字。
  2. 维护活跃度——人数不可得时改用仓库信号：最近 90 天的提交量、 最近 12 个月的发布次数、主要提交者是否仍在。这些数据公开可查，且比人数更贴近 “这个项目是否还有人在维护”这个实际问题。
  3. 明确写明缺口——两者都拿不到时，在“待核验的问题”里写清缺什么， 而不是填一个看起来合理的数字。

没有上述任一类证据时，涉及团队的承诺不得判为“已兑现”。这条规则会让很多案例停在“无法判断”，但那是事实，不是缺陷—— 用一个未经核实的数字把承诺判成兑现，比承认查不到更有害。

维护活跃度数据由 scripts/team-signals.mjs 采集，可在本地复现：node scripts/team-signals.mjs。

06 / 观察名单标准

观察名单不是“未被收购的软件大全”。收录对象必须能提供判断价值，至少满足一条：

  • 有可核验的资金结构（自筹、融资、基金会），且与产品策略相关；
  • 创始团队有公开的独立性或退出表态；
  • 许可证、治理或商业模式发生过值得记录的变化；
  • 产品故事能说明一类独立软件的生存方式。

名单宁少勿多，不接受付费收录，也不以“推荐使用”为目的。归属状态变化时（被收购、关闭、转型）， 会从观察名单移入案例库或标注为已退出。

07 / 更新与纠错

每个案例都有“最后核验”日期。核验间隔目标为 90 天，重大事件（停运、许可证变更、二次收购） 在发生后 30 天内更新。

各条目的核验进度见 核验状态 页。

仓库内置了一套事实校验：pnpm facts 会在每次构建前检查日期精度、对价口径、 带数字信号的来源、核验时效与来源链接格式；CI 也会执行。校验通过不等于内容为真， 但它会阻断最容易出错的那几类问题。

纠错流程：

  1. 在 GitHub 提交 issue，说明哪条事实有误、正确信息是什么、来源在哪里；
  2. 维护者核对来源，必要时联系当事方或回查监管文件；
  3. 通过 PR 修改内容，提交信息中注明依据；
  4. 如涉及结论变化，同步更新证据等级与核验日期。

我们不删除有争议的记录，而是并列呈现不同来源与口径。删除只用于两种情况：来源本身失效， 或内容违反法律与隐私边界。

08 / 许可与数据

结构化数据可从 /cases.json 获取，字段与内容文件一致，便于复用与校对。
