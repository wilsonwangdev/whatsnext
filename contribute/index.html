参与 / Contribute

让记录比叙事更可靠。

这份档案的长期价值，取决于它能否被持续核对。你可以提名一个新案例、纠正一条过期事实， 或者补上某个产品在收购之后的后续。所有修改都通过公开流程完成，并留下来源。

01 / 三种参与方式

提名案例你知道一笔未被收录的交易，且能找到至少一个一手来源。使用案例提名表单。
提交纠错某条事实有误、日期不对、来源失效。使用纠错表单， 注明页面与错误类型。
补充后续已知某个案例在收购后发生了新事件（停运、改许可、二次收购、团队变动）。 直接在对应页面点“提供新信息”，或提交 PR 更新 timeline 与 lastVerified。

02 / 流程

  1. 提名在 Issue 中填写标的、收购方、日期、交易结构与来源链接。不需要写完整文章。
  2. 核验维护者核对一手来源，确认交易结构（整体收购 / 团队加入 / 人才收购）与日期精度； 必要时补充监管文件或联系当事方。
  3. 入库以 PR 提交结构化 Markdown，包含 frontmatter 字段、时间线、来源与“待核验问题”。 CI 会执行构建与 schema 校验。
  4. 复核合并后记录核验日期；90 天内至少回查一次是否有新进展。

争议较大的案例会先在 Discussion 中公开讨论，再决定是否入库。我们允许“存疑”的条目存在， 但必须在页面上明确标注证据等级与未解决问题。

03 / 需要提交什么

每个案例至少需要以下字段。缺失的字段留空，不要猜测：

name产品/公司名，使用公开常用名。
acquirer收购方；如为团队加入，也填接收方。
statuscompleted / announced / team-join / terminated。
dealTypeacquisition / majority-stake / acquihire / team-join / asset-sale。
announcedAt / completedAt公告日与交割日分开；未知就不填。
amount只填官方披露的金额；未披露写 disclosed: false，可在 note 中说明媒体口径。
evidenceA / B / C，标准见方法页。
sources至少一条；优先一手公告、监管文件，其次权威媒体。
timeline只放可核验事件；只有年份时用 dateLabel 标注精度。
openQuestions明确写出还不知道什么，比装作知道更有价值。

04 / 证据要求

  • 一手优先：公司公告、监管文件（20-F、8-K、招股书）、工商登记、官方博客。
  • 媒体只作补充：权威媒体基于登记记录的报道可作 B 级证据；转载与聚合不算新来源。
  • 区分宣布与完成：“宣布收购”与“完成交割”是两条时间线，不能合并。
  • 不要用融资额冒充收购价：这是本档案最常纠正的错误。
  • 来源失效要处理：链接失效时补充存档链接（Wayback Machine），而不是删掉来源。

05 / 表述准则

这份档案要经得起当事方与读者的质疑，因此：

  • 不使用“首个”“最大”“唯一”等无法证伪的定位；
  • 不臆测交易动机，只引用公开表述并注明是谁说的；
  • 不把“团队加入”写成“收购公司”，也不把“收购”降级为“合作”；
  • 对未兑现的承诺，描述事实与日期，不使用嘲讽或道德审判的语气；
  • 涉及个人时，只写与交易相关的公开职业信息。
一条经验法则：如果一句话去掉形容词后信息量不变，就删掉形容词。

06 / 本地开发

站点使用 Astro + Markdown 内容库，所有案例都是仓库里的一个文件。

pnpm install
pnpm dev      # 本地预览
pnpm facts    # 事实核验：日期 / 金额 / 人数 / 来源
pnpm build    # 构建，事实校验或 schema 不通过会失败

内容位置：

  • src/content/cases/*.md：已发生的交易；
  • src/content/watchlist/*.md：尚未易主的观察对象；
  • src/content.config.ts：字段与校验规则。

提交前请运行 pnpm facts --strict 与 pnpm build。 通过意味着字段完整、日期精度与来源匹配、带数字的结构化信号都有来源。 正文里的数字会以 info 形式列出，仍需逐条回查来源。

关于

下一个是谁是一个公开档案，记录开发者软件与开源项目的收购、团队加入，以及交易之后产品、 团队和开源承诺的实际走向。每条核心事实都链接到公开来源，并标注核验日期。
